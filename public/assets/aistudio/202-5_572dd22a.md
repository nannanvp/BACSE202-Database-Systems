# Part I: Distributed Databases (DDBMS)

## 1. Introduction to Distributed Databases

### 1.1 Definitions
- **Distributed Database (DDB):** A collection of multiple, logically interrelated databases distributed over a computer network.
- **Distributed Database Management System (DDBMS):** The software system that manages a distributed database and makes the distribution **transparent** to users.

```text
          +------------------+
          |  Global User /   |
          |   Application    |
          +--------+---------+
                   |  (Sees ONE logical database)
      +------------+------------+
      |  Communication Network  |
      +--+---------+---------+--+
         |         |         |
     +---+---+ +---+---+ +---+---+
     |Site 1 | |Site 2 | |Site 3 |
     | DB_1  | | DB_2  | | DB_3  |
     +-------+ +-------+ +-------+
```

### 1.2 Why Use a DDBMS? (Advantages vs. Challenges)

| Advantages | Challenges / Disadvantages |
| :--- | :--- |
| **Higher Reliability & Availability:** Replication prevents a single site crash from taking down the entire system. | **Increased Complexity & Software Cost:** Requires distributed query optimizers, deadlock detectors, and commit protocols. |
| **Improved Performance:** Data is stored near the sites that use it most (*data localization*), enabling parallel query execution. | **Communication Overhead:** Network latency and message transfers between sites can slow down distributed joins/commits. |
| **Modular Scalability:** Easy to add new sites or expand capacity incrementally without replacing a massive central mainframe. | **Complex Integrity & Security:** Enforcing global constraints and securing data across networks is harder. |
| **Local Autonomy:** Regional branches retain control over their local data while still participating in global queries. | **Concurrency & Recovery Difficulty:** Coordinating locks and atomic commits across unreliable networks is non-trivial. |

### 1.3 Distribution Transparencies
A primary goal of a DDBMS is to hide physical distribution details from users and application developers:
1. **Location Transparency:** Users do not need to know *where* (which site) a data item is physically stored.
2. **Fragmentation Transparency:** Users query the global table as if it were unfragmented, without knowing how it is split horizontally or vertically.
3. **Replication Transparency:** Users interact with a single logical copy; the DDBMS automatically manages multiple physical replicas and keeps them synchronized.
4. **Network / Distribution Transparency:** Combines the above so the system behaves logically like a centralized DBMS.

### 1.4 Distributed Database Design Process
Distributed database design follows **three major steps** (often iterative):
1. **Fragmentation:** Divide the global database relations into smaller logical units called *fragments*.
2. **Allocation:** Decide *where* (at which network sites) each fragment should reside.
3. **Replication:** Decide *whether* and *how many* duplicate copies of fragments should exist across sites.

### 1.5 Homogeneous vs. Heterogeneous DDBMS
- **Homogeneous DDBMS:** All sites run the same DBMS software (e.g., all Oracle or all PostgreSQL) and share a unified global schema. Easier to design and manage.
- **Heterogeneous DDBMS:** Different sites run different DBMS products (e.g., Oracle at HQ, MySQL at branch, MongoDB for logs) and may use different data models or schemas; requires translators/wrappers.

## 2. Distributed Database Architectures

Distributed DBMS architectures are classified along three orthogonal dimensions (Özsu & Valduriez):
- **Autonomy:** Degree to which individual sites operate independently (Tightly Integrated vs. Semiautonomous vs. Totally Isolated).
- **Distribution:** Physical distribution of data across sites (Client-Server vs. Peer-to-Peer).
- **Heterogeneity:** Hardware, OS, DBMS, or data model differences.

### 2.1 Logical & Software Architectures

#### A. Client-Server Architecture
- **Two-Tier:** Clients handle the UI and submit SQL queries over the network to dedicated Database Servers.
- **Three-Tier (Application Tiers):** Separates **User Interface** $\rightarrow$ **Middle Tier (Application Logic / Query Routing)** $\rightarrow$ **Database Layer**.
  - *Note on NoSQL:* Modern distributed/NoSQL systems often shift processing or caching between tiers to remove bottlenecks in the database layer.

#### B. Peer-to-Peer (Fully Distributed) Architecture
- No strict client/server distinction; every node has local DBMS capabilities and participates equally in storing fragments, routing queries, and coordinating transactions.

#### C. Federated / Multidatabase Systems (MDBMS)
- Built on top of existing, autonomous, often heterogeneous local DBMSs.
- A global federation layer translates global queries into local sub-queries without stripping local site autonomy.

### 2.2 Hardware / Memory Sharing Architectures
Crucial distinction explaining why traditional RDBMS struggles to scale out while NoSQL scales horizontally:

```text
  1. Shared Memory              2. Shared Disk              3. Shared Nothing
  (e.g., Oracle 11g)           (e.g., Oracle RAC)             (e.g., NoSQL)

  [P]   [P]   [P]   [P]        [P]   [P]   [P]   [P]       [P]---[P]---[P]---[P]
   |     |     |     |          |     |     |     |         |     |     |     |
   +--+--+--+--+--+--+         [M]   [M]   [M]   [M]       [M]   [M]   [M]   [M]
      |     |     |             |     |     |     |         |     |     |     |
     [M]   [M]   [M]            +--+--+--+--+--+--+        (D)   (D)   (D)   (D)
      |     |     |                |     |     |
     (D)   (D)   (D)              (D)   (D)   (D)

  P = Processor | M = Memory | D = Disk
```

- **Shared Memory:** Multiple CPUs share a single global memory space and disks. Fast communication, but memory bus becomes a severe bottleneck (scales *vertically* only).
- **Shared Disk:** Each CPU has private memory (`M`), but all share a common disk subsystem (`D`). Better fault isolation, but disk interconnect still limits scale.
- **Shared Nothing:** Each node has its **own private CPU, Memory, and Disk**, communicating strictly by message passing over a network. Enables **minimal coordination, independent failure domains, and massive horizontal distribution** (backbone of modern DDBMS and NoSQL).

### 2.3 Centralized vs. Distributed Network Topology
- **Centralized Topology:** All remote nodes connect to one central hub site holding the entire database.
- **Distributed Topology:** Multiple interconnected sites communicate directly across the communication network, each hosting local fragments/replicas.

## 3. Data Fragmentation, Replication, and Allocation Techniques

### 3.1 Data Fragmentation

**Why fragment instead of storing whole tables everywhere?**
- Applications usually access only a *subset* of rows or columns (e.g., Chennai branch only needs Chennai customers).
- Fragmentation reduces storage waste, improves security (sensitive columns stay at HQ), and enables parallel sub-query execution.

#### Correctness Rules of Fragmentation
Any fragmentation of a global relation $R$ into fragments $R_1, R_2, \dots, R_n$ must satisfy three rules:
1. **Completeness:** Every data item (tuple or attribute) in $R$ must appear in at least one fragment $R_i$.
2. **Reconstruction:** There must exist a relational operator that reconstructs $R$ exactly from its fragments.
3. **Disjointness:** Data items should not be duplicated across fragments (except primary keys in vertical fragmentation) so updates are unambiguous.

#### Types of Fragmentation

1. **Horizontal Fragmentation** *(Closest equivalent to NoSQL Sharding)*
   - Splits a relation $R$ into subsets of **rows (tuples)** stored at different sites.
   - **Primary Horizontal Fragmentation:** Defined using Relational Algebra **Selection ($\sigma$)**:
     $$R_i = \sigma_{P_i}(R)$$
     *Example:* `Customer_North = σ_{Region='North'}(Customer)` at Site A; `Customer_South = σ_{Region='South'}(Customer)` at Site B.
   - **Derived Horizontal Fragmentation:** Splits a child relation based on the horizontal fragmentation of a parent relation (via semijoin) so related parent–child rows stay on the same site.
   - **Reconstruction:** Using **Union ($\cup$)**:
     $$R = R_1 \cup R_2 \cup \dots \cup R_n$$

2. **Vertical Fragmentation**
   - Splits a relation $R$ into subsets of **columns (attributes)** stored at different sites.
   - Defined using Relational Algebra **Projection ($\pi$)**, where **every fragment must include the Primary Key ($PK$)** (or tuple ID) to allow lossless reconstruction:
     $$R_i = \pi_{L_i \cup PK}(R)$$
     *Example:* Split `Employee(EmpID, Name, Dept, Salary, TaxID)` into `Emp_Public(EmpID, Name, Dept)` at branch sites and `Emp_Payroll(EmpID, Salary, TaxID)` at HQ.
   - **Reconstruction:** Using **Natural Join ($\bowtie$)**:
     $$R = R_1 \bowtie R_2 \bowtie \dots \bowtie R_n$$

3. **Mixed / Hybrid Fragmentation**
   - Combines both horizontal and vertical fragmentation (e.g., first fragment horizontally by region, then vertically separate public vs. confidential attributes).
   - **Reconstruction:** Apply Natural Joins ($\bowtie$) followed by Unions ($\cup$) (or vice versa, reversing the split order).

### 3.2 Data Replication

**Replication** is the process of maintaining **multiple copies of the same data/fragment** across different servers/sites (called *replicas*).  
**Goals:** High **Availability**, **Fault Tolerance**, **Faster Read Performance**, and **Load Balancing**.

#### Replication Degrees
1. **Non-Replicated (Partitioned):** Zero redundancy; each fragment exists at exactly one site.
2. **Full Replication:** Every fragment is copied to every site in the network ($F_1, F_2, F_3$ exist at Site 1, Site 2, and Site 3).
   - *Pros:* Highest availability, fastest local read queries, excellent fault tolerance.
   - *Cons:* Very high storage cost, high update overhead, complex synchronization.
3. **Partial Replication:** Only selected (e.g., frequently accessed) fragments are replicated at selected sites.
   - *Example:* Data Node 1 holds `P1 (Primary), P2 (Replica)`; Node 2 holds `P2 (Primary), P3 (Replica)`; Node 3 holds `P1 (Replica), P3 (Primary)`. If any node crashes, its partitions are recovered from peer nodes.
   - *Pros:* Best balance between performance and storage; lower synchronization cost than full replication; good availability.
   - *Cons:* Requires replica metadata management and complex allocation decisions.

#### Replication Topologies (How Updates Propagate)

| Topology | How It Works | Advantages | Disadvantages |
| :--- | :--- | :--- | :--- |
| **Master–Slave (Primary–Replica)** | Only the **Primary (Master)** accepts writes. Primary sends updates (e.g., via log) to **Secondaries (Slaves)**, which serve read requests. | Simple architecture; fast read scaling; no write conflicts. | Primary is a write bottleneck; requires **failover/election** if Primary crashes. |
| **Master–Master (Multi-Leader)** | Multiple servers (`Server A <-> Server B`) accept **both reads and writes** and synchronize changes with each other. | No single write bottleneck; higher write availability across regions. | **Conflict resolution** is complex when two masters update the same record concurrently. |

- **Synchronous vs. Asynchronous Replication:**
  - *Synchronous:* Primary waits until replicas confirm the update before acknowledging the client (strong consistency, higher latency).
  - *Asynchronous:* Primary acknowledges immediately and pushes updates to replicas in the background (low latency, risks **replication lag** / stale reads or data loss on primary crash).

### 3.3 Data Allocation Techniques

**Allocation** is the process of deciding **where to store database fragments** across multiple network sites.  
**Objectives:** Reduce query response time, improve availability & reliability, balance workload, minimize communication cost, and maximize overall system performance.

#### Factors Affecting Allocation
According to standard database literature (*Elmasri & Navathe*):
- **Frequency of data access** (Which site reads a fragment most?)
- **Read/Write ratio & Update frequency** (How often is data modified?)
- **Communication cost** (Network bandwidth and latency between sites)
- **Storage capacity** and **Processing capability** at each site
- **Reliability and availability requirements**
- **Load balancing** across sites
- **Security and privacy considerations**

#### Standard Allocation Strategies

1. **Centralized Allocation**
   - **Description:** The entire database is stored at **one central site** (zero duplication); remote sites access it over the network.
   - **Characteristics:** Simplest strategy, easy consistency maintenance, no duplication.
   - **Suitable For:** Small organizations, centralized apps, low network traffic. (e.g., University storing all student records solely on the main campus server).
   - **Pros:** Easy management, low storage cost, simple backup/security.
   - **Cons:** **Single point of failure**, high network traffic, poor availability if central site goes down.

2. **Non-Replicated (Partitioned) Allocation**
   - **Description:** Each fragment has **exactly one owner site** and exists only once.
   - **Example:** Customer records partitioned by region: `North -> Site A`, `South -> Site B`, `East -> Site C`, `West -> Site D`.
   - **Pros:** No replica maintenance, storage efficient, faster updates, easy concurrency control.
   - **Cons:** Reduced availability (if Site B fails, South data is unavailable), high communication cost for remote/cross-site queries.
   - **Suitable For:** Write-heavy systems with frequent updates or limited storage.

3. **Replicated Allocation (Full & Partial)**
   - **Description:** One or more fragments are stored at **multiple sites** (using Full or Partial Replication strategies described in Section 3.2).

#### Allocation vs. Replication (Conceptual Distinction)

| Allocation | Replication |
| :--- | :--- |
| Decides **where** a fragment is stored | Decides **how many copies** are stored |
| Focuses on minimizing communication cost & localizing access | Focuses on improving availability & fault tolerance |
| Does not necessarily create duplicate copies | Explicitly creates duplicate copies |

#### Comparison of the Four Allocation Techniques

| Technique | Data Copies | Storage Cost | Query Speed | Update Cost | Availability |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Centralized** | One copy at one site | Low | Slow for remote users | Low | Low |
| **Non-Replicated (Partitioned)** | One copy of each fragment | Low | Depends on fragment location | Low | Medium |
| **Partial Replication** | Copies at selected sites | Medium | Fast | Medium | High |
| **Full Replication** | Copy at every site | Very High | Very Fast | Very High | Very High |

#### Allocation Strategies Based on Workload Access Patterns

| Workload Type | Real-World Examples | Recommended Strategy | Justification |
| :--- | :--- | :--- | :--- |
| **Read-Intensive** | Online shopping catalog, digital library, news portal | **Replicated Allocation** | Most ops are reads; local copies eliminate network delay. |
| **Write-Intensive** | Banking, airline reservation, hospital management | **Non-Replicated Allocation** | Avoids expensive replica synchronization; faster updates. |
| **Mixed Workloads** | University ERP, e-commerce systems, enterprise apps | **Partial Replication** | Replicate hot/read-heavy data; keep write-heavy/cold data at single sites. |

#### Cost Considerations & Textbook Design Guidelines
- **5 Allocation Costs to Minimize:** *Communication Cost* (network transfer), *Storage Cost* (disk for fragments/replicas), *Processing Cost* (CPU for distributed queries), *Update Cost* (synchronizing replicas), and *Reliability Cost* (maintaining service despite crashes).
- **Design Guidelines:** Store fragments close to users; replicate frequently read data; avoid unnecessary replication for frequently updated data; minimize communication overhead; balance workload; ensure high availability & fault tolerance; minimize unnecessary storage redundancy.

## 4. Transaction Management, Concurrency Control, and Recovery

### 4.1 Distributed Transaction Architecture
- A **Global Transaction** accesses data across multiple sites.
- **Transaction Manager (Coordinator):** Runs at the site where the transaction originates; breaks the global transaction into sub-transactions and coordinates commit/abort across sites.
- **Resource Managers (Local Participants):** Execute local sub-transactions at each participating site and manage local logs and locks.

### 4.2 Distributed Concurrency Control

#### A. Distributed Lock-Based Protocols (Extending 2PL)
1. **Centralized Two-Phase Locking (2PL):**
   - A single site hosts the **Central Lock Manager** for the entire DDBMS.
   - *Pros:* Simple deadlock detection (single global wait-for graph). *Cons:* Bottleneck and single point of failure.
2. **Primary Copy 2PL:**
   - One site is designated as the **primary copy site** for each data item (or fragment). Lock requests for item $X$ go only to $X$'s primary site, even if $X$ is replicated elsewhere.
   - *Pros:* Distributes lock management load without requiring locks on every replica. *Cons:* Updates still must propagate to replicas.
3. **Distributed 2PL:**
   - Every site runs its own lock manager for data stored locally.
   - For replicated data, two main strategies exist:
     - **ROWA (Read-One, Write-All):** Read any single replica (shared lock on 1 site), but writes must lock and update **all** replicas (high write overhead, fails if one replica is down).
     - **Quorum Consensus (Majority Locking):** To read, acquire read locks from $N_r$ replicas; to write, acquire write locks from $N_w$ replicas such that $N_r + N_w > N$ and $N_w > N/2$ (where $N$ = total replicas). Guarantees read and write quorums always intersect at $\ge 1$ up-to-date node.

#### B. Distributed Timestamp Ordering
- Every transaction receives a **globally unique timestamp**: $\text{TS}(T_i) = \langle \text{local\_clock}, \text{site\_id} \rangle$ (using **Lamport clocks** to keep logical clocks ordered across sites).
- Sites enforce timestamp order locally without needing global lock tables.

#### C. Distributed Deadlock Handling
- **Deadlock Prevention (No cycles possible):**
  - **Wait-Die (Non-preemptive):** Older $T_1$ waits for younger $T_2$; younger $T_1$ requesting lock held by older $T_2$ dies (aborts & restarts with same timestamp).
  - **Wound-Wait (Preemptive):** Older $T_1$ wounds (forces abort of) younger $T_2$; younger $T_1$ waits for older $T_2$.
- **Deadlock Detection:**
  - Individual sites maintain Local Wait-For Graphs (LWFGs), which can miss cross-site cycles (e.g., $T_1$ at Site A waits for $T_2$ at Site B, which waits for $T_1$ at Site A).
  - Periodically combined into a **Global Wait-For Graph (GWFG)** using *Centralized*, *Hierarchical*, or *Distributed* detection algorithms to break cycles.

### 4.3 Distributed Recovery and Atomic Commit Protocols

A distributed transaction must satisfy **Atomicity** across all sites: either **all** sites commit or **all** sites abort, despite site crashes or lost messages.

#### A. Two-Phase Commit (2PC)
The standard protocol using a **Coordinator ($C$)** and **Participants ($P_1, \dots, P_n$)**:

```text
  Coordinator (C)                        Participants (P_i)
        |                                        |
        |--------- 1. PREPARE (Phase 1) -------->|  (Write UNDO/REDO to WAL)
        |<-------- 2. VOTE-COMMIT / ABORT -------|  (Log READY if committing)
        |                                        |
   [Write COMMIT                                 |
    or ABORT to WAL]                             |
        |                                        |
        |--------- 3. GLOBAL COMMIT/ABORT ------>|  (Apply decision, release locks)
        |<-------- 4. ACK (Phase 2) -------------|  (Write END to WAL)
```

- **Phase 1 (Voting / Prepare Phase):**
  1. Coordinator writes `BEGIN_COMMIT` to its log and sends `PREPARE` to all participants.
  2. Each participant checks if it can safely commit. If yes, it **force-writes** its undo/redo log records and a `READY` record to disk (WAL) and replies `VOTE-COMMIT`. Otherwise, it logs `ABORT` and replies `VOTE-ABORT`.
- **Phase 2 (Decision / Commit Phase):**
  1. If **all** participants reply `VOTE-COMMIT`, Coordinator force-writes `COMMIT` to its log and sends `GLOBAL-COMMIT` to all participants. If any replies `VOTE-ABORT` (or times out), Coordinator logs `ABORT` and sends `GLOBAL-ABORT`.
  2. Participants log the decision, commit/abort locally, release locks, and send `ACK`. Coordinator writes `END` once all ACKs arrive.

- **Major Limitation of 2PC — It is a Blocking Protocol!**
  - If a participant has sent `VOTE-COMMIT` (entering the *uncertain/ready* state) and **the Coordinator crashes** before sending the Phase 2 decision, the participant **cannot unilaterally abort or commit** (because another participant might have received the opposite decision or crashed). It remains **blocked**, holding locks indefinitely until the Coordinator recovers.

#### B. Three-Phase Commit (3PC)
- Solves 2PC's blocking problem under **fail-stop crashes (no network partitions)** by splitting Phase 2 into two phases:
  1. **Phase 1 (`CanCommit?`):** Same voting step (`YES` / `NO`).
  2. **Phase 2 (`PreCommit`):** If all vote `YES`, Coordinator sends `PREPARE-TO-COMMIT` (`PreCommit`). Participants enter a *prepared-to-commit* state and ACK. (No site commits yet, and no site can still be unaware of unanimous `YES` once `DoCommit` starts).
  3. **Phase 3 (`DoCommit`):** Coordinator sends final `GLOBAL-COMMIT`.
- **Why Non-Blocking?** If the Coordinator crashes, a newly elected Coordinator can query survivors: if no one is in `PreCommit`, safely abort; if at least one is in `PreCommit`, safely commit. *(Note: 3PC still cannot guarantee safety + liveness under arbitrary network partitions—consistent with CAP/FLP impossibility).*

## 5. Distributed Query Processing and Optimization

### 5.1 Cost Model in Distributed Queries
Unlike centralized DBMS (dominated by Disk I/O), distributed query cost is heavily dominated by **Communication (Data Transfer) Cost** over the network:
$$\text{Total Cost} = C_{\text{CPU}} + C_{\text{I/O}} + C_{\text{COMM}}$$
where communication cost for transferring data of size $X$ bytes is:
$$C_{\text{COMM}}(X) = C_0 + C_1 \times X$$
($C_0$ = startup message latency cost, $C_1$ = per-byte transmission cost).

### 5.2 Phases of Distributed Query Optimization
1. **Query Decomposition:** Parse SQL, check syntax/semantics, normalize predicates, convert into an initial algebraic query tree.
2. **Data Localization:** Replace global relations in the query tree with their fragment reconstruction expressions (e.g., $R_1 \cup R_2$), then push selections/projections down to **prune unnecessary fragments** (e.g., if `WHERE Region = 'North'`, drop `Customer_South` immediately).
3. **Global Query Optimization:** Choose the optimal **join ordering**, **copy selection** (which replica to read), and **data movement strategy** to minimize network traffic.
4. **Local Query Optimization:** Each participating site optimizes its local sub-query using standard local B+ tree indexes and cost-based plans.

### 5.3 Distributed Join Strategies & The Semijoin ($\ltimes$) Technique

Suppose Site 1 holds $R(A, B)$ and Site 2 holds $S(A, C)$, and we want $R \bowtie_A S$ at Site 1.

1. **Ship-Whole:** Send all of $S$ from Site 2 to Site 1, then join locally. Wasteful if only a tiny fraction of $S$'s tuples match $R$.
2. **Fetch-as-Needed:** Scan $R$ at Site 1; for each tuple, request matching tuples from Site 2. High latency (many small messages).
3. **Semijoin Optimization ($S \ltimes_A R$):**
   The **semijoin** of $S$ with $R$ on attribute $A$ returns only those tuples of $S$ that match at least one tuple in $R$:
   $$S \ltimes_A R = \pi_S(S \bowtie_A R) = S \bowtie_A \pi_A(R)$$

#### Worked Numerical Example: Join vs. Semijoin
- **Setup:**
  - Site 1 has `Dept(Dno, Dname, Budget)`: $100$ tuples, $50$ bytes/tuple $\implies 5{,}000$ bytes.
  - Site 2 has `Emp(Eid, Ename, Salary, Dno)`: $10{,}000$ tuples, $100$ bytes/tuple $\implies 1{,}000{,}000$ bytes ($1$ MB).
  - Attribute `Dno` is $4$ bytes. Suppose we want `Dept ⋈_{Dno} Emp` for `Budget > 50L`, which matches only **$5$ departments** and **$80$ employees**.
- **Method A (Ship-Whole `Emp` to Site 1):**
  - Transfer entire `Emp` table: **$1{,}000{,}000$ bytes**.
- **Method B (Semijoin `Emp ⋉ Dept'`):**
  1. At Site 1, filter `Dept' = σ_{Budget > 50L}(Dept)` ($5$ tuples).
  2. Project only join key $\pi_{\text{Dno}}(\text{Dept}')$ and ship to Site 2: $5 \times 4 = \mathbf{20\text{ bytes}}$.
  3. At Site 2, compute $\text{Emp}' = \text{Emp} \ltimes_{\text{Dno}} \pi_{\text{Dno}}(\text{Dept}')$ ($80$ matching tuples) and ship $\text{Emp}'$ to Site 1: $80 \times 100 = \mathbf{8{,}000\text{ bytes}}$.
  4. At Site 1, perform final join $\text{Dept}' \bowtie_{\text{Dno}} \text{Emp}'$.
  - **Total Data Transferred:** $20 + 8{,}000 = \mathbf{8{,}020\text{ bytes}}$ (over **99% reduction** in network traffic!).

# Part II: NoSQL Databases

## 6. Introduction and Evolution of NoSQL

### 6.1 What is NoSQL?
- **NoSQL ("Not Only SQL" / "NoREL"):** An approach to database design enabling storage and querying of data outside the rigid tabular structures of traditional Relational DBMSs (RDBMS).
- **Origin:** The term **NoSQL** was introduced by **Carlo Strozzi** in **1998** (for a lightweight open-source relational DB without a SQL interface) and popularized in **2009** by internet giants (Google, Facebook, Amazon) facing massive web-scale workloads.
- **Key Takeaway:** Choosing SQL vs. NoSQL is **contextual**—depends on data structure, scale, consistency, and query requirements.

#### What NoSQL is NOT
- It is **not** strictly about banning the SQL language (many NoSQL DBs offer SQL-like dialects).
- It is **not** only open source, not only for "big data," not only about cloud computing, not merely clever use of RAM/SSD, and not a single elite group of products.

### 6.2 Three Generations of Database Revolutions

```text
  [1960s-70s: 1st Gen]  --->  [1970s-90s: 2nd Gen]  --->  [2000s-10s: 3rd Gen]  --->  [Present+]
  Navigational DBMS           Relational DBMS             NoSQL & Big Data            Modern Data Stack
  (Hierarchical / Network)    (Codd, SQL, ACID)           (Scale-Out, CAP/BASE)       (Cloud Lakes, AI/ML)
```

1. **First Generation: Navigational Databases (1960s–1970s)**
   - Evolved from **flat-file systems** (punched cards, magnetic tapes with massive redundancy).
   - **Hierarchical Model (e.g., IBM's IMS):** Inverted tree structure, strict **1:N (one-to-many)** parent–child links (e.g., `Department -> Courses -> Professors`). Must navigate from root down branches.
   - **Network Model (e.g., CODASYL):** Generalized graph structure supporting **M:N (many-to-many)** links with multiple parents and children (e.g., `Employee <-> Department`).
   - *Pros:* Faster than flat files, reduced redundancy, better integrity.
   - *Limitations:* Complex procedural programming (telling computer *how* to physically follow pointers), difficult maintenance, poor flexibility, no standard query language.

2. **Second Generation: The Relational Revolution (1970s–1990s)**
   - Proposed by **Edgar F. Codd (1970)** — separated **logical view** (tables/relations) from **physical storage** (files/indexes).
   - **Declarative SQL:** Users state *what* data they want; the query optimizer decides *how* to fetch it.
   - **Normalization & ACID:** Eliminated redundancy and guaranteed strict banking/ERP transaction integrity.
   - *IDC Platform Mapping:* 1st Platform = Mainframes (Hierarchical/Network/ISAM) $\rightarrow$ 2nd Platform = Client-Server/Web 1.0 (RDBMS) $\rightarrow$ 3rd Platform = Cloud, Social, Big Data, Mobile, IoT (RDBMS + NoSQL + NewSQL).

3. **Third Generation: NoSQL & Big Data (2000s–2010s)**
   - Triggered by the explosion of social media, e-commerce, and IoT. Single-node RDBMSs cracked under **four business pressures**:
     1. **Volume:** Terabytes/petabytes of user/sensor data exceeding single-server capacity.
     2. **Velocity:** High-speed real-time read/write streams (likes, clicks, telemetry).
     3. **Variability:** Diverse unstructured/semi-structured data that doesn't fit rigid fixed-column tables.
     4. **Agility:** Rapidly evolving schemas as business requirements change quickly.
   - Vertical scaling (*Scale-Up*: adding RAM/CPU/HDD to one expensive machine) hit physical/cost walls, forcing **Horizontal Scaling (*Scale-Out*: adding commodity servers)**.

### 6.3 Foundational NoSQL Industry Case Studies

| System / Standard | Business Driver | Key Finding / Innovation |
| :--- | :--- | :--- |
| **LiveJournal's Memcache** | Needed faster database query performance. | Hashing & caching data in shared RAM drastically cuts read requests hitting the DB. |
| **Google's MapReduce** | Index billions of web pages using low-cost hardware. | Parallel processing across many commodity processors indexes massive data quickly. |
| **Google's Bigtable** | Flexibly store massive tabular data in a distributed system. | Sparse matrix model (billions of rows, millions of columns) without up-front schema design. |
| **Amazon's Dynamo** | Accept web shopping orders 24×7 globally. | Simple replicated key-value store stays write-available even during large traffic/failures. |
| **MarkLogic** | Query large XML document collections on commodity nodes. | Distributed query evaluation against local disk indexes on each commodity server. |

## 7. Characteristics of NoSQL Systems

1. **Non-Relational & Aggregate-Oriented:** Stores related data together rather than splitting across normalized tables; eliminates object-relational impedance mismatch and cross-node `JOIN`s.
2. **Schema-Free / Dynamic (Implicit) Schema:** Different records in the same collection/table can store different fields/attributes without `ALTER TABLE` downtime.
3. **Horizontal Scalability (Scale-Out):** Built on **Shared-Nothing architecture** using cheap commodity servers; adding nodes linearly expands storage and throughput.
4. **Auto-Sharding:** Natively partitions data and query loads automatically across cluster nodes.
5. **Built-in Replication & High Availability:** Automatically maintains multiple copies across racks/data centers to survive hardware crashes.
6. **Relaxed / Tunable Consistency (BASE):** Trades strict immediate consistency during failures for ultra-low latency and high availability.

## 8. The CAP Theorem and Consistency Models

### 8.1 Eric Brewer's CAP Theorem
The **CAP Theorem** states that in a distributed system with replicated data, it is **impossible to simultaneously guarantee all three** of the following properties:
- **C — Consistency (Linearizability):** Every read receives the most recent write or an error. Every client sees the exact same view of the data regardless of which server responds.
- **A — Availability:** Every non-failing node returns a non-error response in a reasonable amount of time (without guaranteeing it contains the most recent write).
- **P — Partition Tolerance:** The system continues operating even if a network fault drops/delays messages and splits the cluster into disconnected partitions.

> **Core Rule:** Because network partitions (**P**) are unavoidable in real distributed networks:  
> - If there is **NO partition** $\rightarrow$ **CA** is possible.  
> - When a **partition OCCURS** $\rightarrow$ the system must choose either **CP** or **AP**, never both.

### 8.2 Real-Life Analogies (Why "CA" Fails Under Partitions)

#### Analogy 1: Two Bank Branches (`Branch A <---- Internet ----> Branch B`)
- **Case 1 (Network Working):** Both branches communicate $\rightarrow$ same balance shown and customers served (**looks like CA**).
- **Case 2 (Network Cable Breaks = Partition $P$):** Suppose Balance = ₹10,000. You withdraw ₹10,000 at Branch A; immediately someone tries to withdraw at Branch B, which cannot reach Branch A:
  - **Option 1 — Choose Consistency (CP):** Branch B says *"Sorry, cannot verify balance while network is down."* No overdraft occurs; data stays correct, but service is unavailable.
  - **Option 2 — Choose Availability (AP):** Branch B allows the withdrawal anyway. Both give ₹10,000 (Balance becomes -₹10,000). Customer is served, but data is temporarily inconsistent.

#### Analogy 2: Phone Call for the Last Movie Ticket
- You and a friend want to book the last ticket. If the phone works, you coordinate (**CA**). If the phone network fails (**P**), either one refuses to book until reconnected (**CP**) or both risk double-booking (**AP**).

*Note:* A **single-server RDBMS** (e.g., one MySQL instance) has no distributed replicas to partition, so it provides **CA**—but CAP specifically governs **distributed** systems.

### 8.3 CAP Classification of Databases

```text
                       [ C ] Consistency
                        / \
        CA             /   \             CP
  (Single-Node /      /     \     (Refuses stale writes/reads
   No Partition)     /       \     during partition)
  MySQL, Postgres,  /  Pick 2 \   MongoDB, HBase, Redis,
  SQL Server,      /___________\  Google Bigtable
  MariaDB        [ A ]         [ P ]
               Availability   Partition Tolerance
                        AP
         (Remains available with stale reads; syncs later)
          Cassandra, CouchDB, Amazon DynamoDB, Riak, Voldemort
```

*(Exam Clarification: Systems like MongoDB default to CP via single-primary + majority elections, while DynamoDB and Cassandra default to AP/eventual consistency, though many modern NoSQL DBs allow tuning consistency per query.)*

### 8.4 Classroom CAP Decision Scenarios

| Scenario | Problem During Partition / Delay | Best Choice | CAP Type |
| :--- | :--- | :--- | :--- |
| **1. Bank ATM** | Customer empties account at ATM A; network to ATM B fails. | Reject withdrawal at ATM B until balance verified. | **CP** |
| **2. Instagram Likes** | You like a post; friend's phone briefly shows old like count. | Keep showing post; update count after synchronization. | **AP** |
| **3. Flight Booking** | Only 1 seat left; booking servers cannot communicate. | Temporarily stop booking until seat status is confirmed. | **CP** |
| **4. Hospital Allergy Record** | Allergy updated seconds ago; another hospital cannot access latest record. | Wait until latest record can be verified before prescribing. | **CP** |
| **5. Google Maps Traffic** | Traffic data from one road is delayed by a network issue. | Continue providing navigation with best available data. | **AP** |

### 8.5 Distributed Consistency & Eventual Consistency

In distributed systems, updates are delayed across nodes by **network latency, server failures, network partitions, or heavy workloads**. How the system handles this temporary disagreement defines its consistency model:

- **Eventual Consistency:** After an update, replicas may temporarily hold different values, **but if no new updates occur, all replicas eventually converge to the same value**.
  - *Example:* Social post has `100` likes on Servers A, B, C. User likes post $\rightarrow$ Server A = `101`, B = `100`, C = `100` $\rightarrow$ after sync, all show `101`.
  - *Why allow it?* Immediate global synchronization increases latency and reduces availability.
  - *Suitable For:* Social-media like/view counters, product recommendations, ratings, analytics, activity feeds, cached info.

| Strong / Immediate Consistency | Eventual Consistency |
| :--- | :--- |
| Prioritizes latest committed data | Temporary stale values may be observed |
| Requires more inter-node coordination | Requires less immediate coordination |
| Can increase latency / reduce availability during partitions | Improves responsiveness and availability |
| Crucial when exact latest value is mandatory | Ideal when brief discrepancies are acceptable |
| *Example:* Bank account balance, critical inventory stock | *Example:* Social-media like counter, view counts |

## 9. ACID vs BASE Properties

### 9.1 ACID ("The Perfectionist" — Traditional RDBMS)
- **A — Atomicity (All-or-Nothing):** Either all operations of a transaction succeed or all roll back (even on disk/network crash).
  - *Bank Transfer Example:* Deducting ₹5,000 ($100) from Account A and adding to Account B must both happen, or money is restored to A.
- **C — Consistency Preservation:** Transaction transforms the database from one valid state to another, preserving all integrity constraints (e.g., total sum across A and B remains unchanged).
- **I — Isolation:** Concurrent transactions execute independently; intermediate changes are hidden until commit (prevents dirty reads / cascading rollbacks).
- **D — Durability:** Once committed, changes persist permanently despite subsequent power failures or crashes.

### 9.2 BASE ("The Realist" — Distributed NoSQL)
To maximize horizontal scalability and availability, NoSQL adopts **BASE**:
- **BA — Basically Available:** The system appears to work most of the time; even during partial node failures, the rest of the system continues serving requests.
- **S — Soft State:** Data state can change over time *even without new user input* due to background replica synchronization.
- **E — Eventual Consistency:** The system will eventually become consistent across all nodes once updates stop and synchronization completes.
  - *Instagram Likes Example on Cassandra:* You tap "Like" $\rightarrow$ nearest server records `10,001` instantly. Your friend overseas reads `10,000` for a second because sync hasn't finished; a few moments later, everyone sees `10,001` without freezing the app.

### 9.3 ACID vs. BASE Summary Table

| Feature | ACID (SQL / RDBMS) | BASE (NoSQL) |
| :--- | :--- | :--- |
| **Philosophy** | Pessimistic: *"Anything might go wrong—get every detail right."* | Optimistic: *"Focus on throughput; failed syncs will catch up."* |
| **Concurrency Mechanism** | Heavy locking (`locks & unlocks`), blocks conflicting reports | Avoids locks, **never blocks a write** |
| **Consistency Timing** | Immediate / Strong at transaction commit | Eventual (weak / soft state temporarily allowed) |
| **CAP Priority** | Consistency & Isolation | Availability & Partition Tolerance |
| **Best Use Cases** | Banking, ERPs, flight seat booking, medical prescriptions | Social feeds, likes, IoT streams, product catalogs, caching |

## 10. NoSQL Modeling Techniques

### 10.1 Aggregate Data Models
In relational databases, data is normalized into flat tuples across many tables (`Orders`, `OrderItems`, `Customer`, `Address`), creating an **impedance mismatch** with in-memory application objects and requiring expensive multi-node `JOIN`s in distributed clusters.

- **Aggregate:** A collection of related domain objects treated as a **single unit** for data manipulation, atomic updates, and cluster distribution (e.g., an `Order` document embedding customer summary + line items + shipping address).
- **Aggregate-Oriented Databases:**
  - **Key-Value, Document, and Column-Family** databases are *aggregate-oriented*: each key/document/row-key bundles an entire aggregate onto a single node/shard so reads and writes stay fast and local.
- **Aggregate-Ignorant Databases:**
  - **Relational** and **Graph** databases are *aggregate-ignorant*: data is fine-grained (tables or nodes/edges) and freely traversed from multiple angles.

#### Document Modeling: Embedding vs. Referencing

| Approach | How It Works | Best Used When... | Drawbacks |
| :--- | :--- | :--- | :--- |
| **Embedding (Denormalized)** | Store related sub-objects/arrays directly inside the parent document (e.g., blog post + `comments` array). | 1:1 or 1:Few relationships; data is always read together; updates are localized. | Data duplication if shared widely; risk of hitting **16 MB** document limit if array grows unbounded. |
| **Referencing (Normalized)** | Store `_id` references in separate collections and resolve via application code or `$lookup`. | 1:Many (unbounded) or M:N relationships; referenced entity changes frequently or is accessed independently. | Requires extra queries or `$lookup` (slower across sharded clusters). |

---

### 10.2 Distribution Models

NoSQL systems distribute data using two **orthogonal** techniques: **Sharding** (splitting data) and **Replication** (copying data).

#### A. Sharding vs. Replication

| Feature | Sharding (Horizontal Partitioning) | Replication |
| :--- | :--- | :--- |
| **Purpose** | Scale storage capacity and write throughput | Improve availability, fault tolerance, and read speed |
| **Data Stored** | **Different** subsets of data on each server | **Same** data copies across multiple servers |
| **Primary Goal** | Horizontal scalability (Scale-Out) | High availability & backup |
| **Increases Storage Capacity?** | **Yes** | **No** |
| **Improves Read Performance?** | Limited (speeds up targeted shard queries) | **Yes** (reads distributed across replicas) |
| **Improves Write Performance?** | **Yes** (writes spread across shards) | Limited (Primary handles writes in Primary–Replica) |
| **Data Redundancy?** | **No** (single copy per shard unless replicated) | **Yes** |
| **Fault Tolerance** | Low (unless each shard is also replicated) | **High** |

#### B. Sharding Architecture & Strategies
Client requests pass through a **Query Router** (e.g., `mongos`), which uses the **Shard Key** to route reads/writes to the target shard:

```text
                 [ Client Application ]
                          |
                    [ Query Router ]
               (Routes via Shard Key)
         +----------------+----------------+
         |                |                |
   [ Shard 1 ]      [ Shard 2 ]      [ Shard 3 ]
  (IDs 1-1000)    (IDs 1001-2000)  (IDs 2001-3000)
```

**Three Sharding / Partitioning Techniques:**
1. **Range-Based Sharding:**
   - Divides data by contiguous key ranges (`1–1000 -> Shard 1`, `1001–2000 -> Shard 2`).
   - *Pros:* Easy implementation; **efficient range queries**.
   - *Cons:* **Uneven distribution / hotspots** if most new inserts fall in the latest range (e.g., timestamps or auto-increment IDs).
2. **Hash-Based Sharding:**
   - Applies a hash function (or **consistent hashing** ring) to the shard key: $\text{Hash}(\text{StudentID}) \rightarrow \text{Shard } 2$.
   - *Pros:* **Uniform data distribution**, prevents server overload.
   - *Cons:* **Poor support for range queries** (adjacent keys scatter across different shards; requires scatter–gather across all shards).
3. **Directory-Based Sharding:**
   - Uses a lookup table mapping specific keys to shards (`Student 101 -> Shard 2`, `Student 205 -> Shard 1`).
   - *Pros:* Highly flexible; easy to relocate data dynamically.
   - *Cons:* Overhead and single-point dependency of maintaining the directory service.

#### C. Shard Key Selection & The "Hot Shard" Problem
A good **Shard Key** (e.g., `customerId`, `studentId`, `userId`, `productId`) must:
1. Distribute data **evenly** (high cardinality & uniform distribution).
2. **Avoid hotspots** (don't funnel all writes to one shard).
3. **Support frequent queries** directly (avoid scatter–gather).

> **Case Study — Poor Shard Key (`city`):**  
> An e-commerce collection with **500 million orders** is sharded by `city`. Suppose traffic is: **Chennai = 35–50%**, **Bengaluru = 25–30%**, **Mumbai = 15–20%**, **Others = 10–15%**.  
> The Chennai shard receives half of all reads/writes and becomes overloaded! This is called **data skew / workload skew**, creating a **Hot Shard**.  
> *Lesson:* Sharding does not automatically guarantee scalability—a poor shard key simply moves the bottleneck from one server to one shard.

#### D. Combined Distribution Models
In production NoSQL systems, **Sharding and Replication are combined**:
- **Sharded Primary–Replica (e.g., MongoDB):** Each shard is itself a **Replica Set** (1 Primary + multiple Secondaries). Sharding scales writes/storage, while replication guarantees each shard survives crashes.
- **Peer-to-Peer Ring (e.g., Cassandra, Dynamo):** Every node is equal (no master); data is hash-sharded around a consistent-hashing ring, and each partition is automatically replicated to $N$ adjacent clockwise nodes.

### 10.3 MapReduce

**MapReduce** (pioneered by Google) is a parallel distributed processing paradigm used in NoSQL/Big Data ecosystems to process massive datasets across clusters of commodity hardware by moving **computation to where the data lives**.

#### How MapReduce Works (3 Core Phases)
1. **Map Phase:** Input data chunks are processed in parallel across nodes. A user-defined `map(k1, v1)` function emits intermediate `(key, value)` pairs: `list(k2, v2)`.
2. **Shuffle & Sort Phase:** The framework automatically groups and sorts all intermediate pairs by key `k2`, transferring values with the same key to the same Reducer node: `(k2, list(v2))`.
3. **Reduce Phase:** A user-defined `reduce(k2, list(v2))` function aggregates the grouped values for each key and emits final results: `list(k3, v3)`.

```text
  Input Chunks          MAP                 SHUFFLE & SORT            REDUCE            Output
  [Chunk 1: "CSE, ECE"] ---> ("CSE", 1) --\
                             ("ECE", 1) ---+--> ("CSE", [1, 1]) ---> ("CSE", 2)
  [Chunk 2: "CSE, IT" ] ---> ("CSE", 1) --/
                             ("IT",  1) ------> ("ECE", [1])    ---> ("ECE", 1)
                                                ("IT",  [1])    ---> ("IT",  1)
```

#### Worked Example: Total Order Revenue by City
Suppose orders are spread across 3 shards:
- **Map:** For each order `{orderId, city, amount}`, emit `(city, amount)`.
  - Shard 1 emits: `("Chennai", 4500)`, `("Mumbai", 2000)`
  - Shard 2 emits: `("Chennai", 1500)`, `("Bengaluru", 3000)`
- **Shuffle & Sort:** Groups by `city`:
  - `"Bengaluru" -> [3000]`
  - `"Chennai" -> [4500, 1500]`
  - `"Mumbai" -> [2000]`
- **Reduce:** Sums each list:
  - `("Bengaluru", 3000)`, `("Chennai", 6000)`, `("Mumbai", 2000)`.

### 11.1 Side-by-Side Overview & Real-Time Examples

| :--- | :--- | :--- | :--- | :--- |
| **Key-Value Store** | `Key -> Value` (hash table; fast lookup) | **Redis**, Amazon DynamoDB, Riak, Memcached, Scalaris | OTP storage, login sessions, shopping carts, cache, leaderboards, chat state | `mobile_9876543210 -> 458921` <br> `cart_25 -> {item1, item2}` |
| **Document Database** | JSON / BSON / XML documents | **MongoDB**, CouchDB, Couchbase, Google Firestore, MarkLogic | Student records, e-commerce catalogs, hospital records, blogs, user profiles, ride-sharing trips | `{ "rollNo": "22BCE101", "name": "Rahul", "skills": ["Python", "MongoDB"] }` |

### 11.2 Key-Value Databases
- **Data Model:** Simplest NoSQL model—functions like a giant distributed hash table where each unique **key** points to an opaque **value** (string, JSON, or BLOB).
- **Strengths:** Ultra-fast $O(1)$ lookup/insert by key; highly partitionable; achieves extreme horizontal scale (e.g., DynamoDB auto-allocates partitions as tables fill).
- **Limitations:** Value is opaque (cannot easily query or filter inside the value without indexing extensions); unsuitable for complex multi-attribute queries.
- **Classic Use Cases:** Facebook login session storage (Redis), Amazon temporary shopping carts (Redis), gaming leaderboards, WhatsApp cached chat state, OTP tokens.

### 11.3 Column-Based (Wide-Column / Extensible Record) Databases
- **Data Model:** Inspired by **Google's Bigtable** paper. Uses tables, row keys, and **column families**, **but unlike RDBMS, column names and formats can vary from row to row** within the same table (sparse matrix).
  - *Example:* Row `Bob` has `{emailAddress, gender, age}`; Row `Britney` has `{emailAddress, gender}`; Row `Tori` has `{emailAddress, country, hairColor}`.
- **Strengths:** Massive write throughput; columns are stored/processed together so aggregation queries (`SUM`, `COUNT`, `AVG`, `MIN`) and time-series scans are very fast; ideal for data warehouses, BI, and append-heavy logs.
- **Limitations:** Not flexible for ad-hoc individual document modeling or relational joins.
- **Classic Use Cases:** Millions of banking transaction logs (Cassandra), billions of telecom Call Detail Records/CDRs (HBase), Netflix recommendation watch logs (Cassandra), IoT weather/factory sensor readings (HBase).

### 11.4 Graph Databases
- **Data Model:** Uses **Nodes** (entities), **Edges** (directed relationships), and **Properties** (key-value pairs on nodes/edges). Every node and edge has a unique identifier.
- **Strengths:** Relationships are stored as direct physical pointers (*index-free adjacency*), enabling multi-hop traversals ("friends of friends", shortest path, fraud rings) in constant/single-operation speed rather than expensive recursive SQL `JOIN`s.
- **Limitations:** Harder to shard horizontally across many servers due to densely interconnected edges; overkill for simple attribute filtering.
- **Classic Use Cases:** Social networks (LinkedIn, Facebook, Twitter), banking fraud detection (unusual transaction rings in Neo4j), Netflix movie/interest graphs, Google Maps shortest-path navigation & logistics routing.

### 11.5 Quick Selection Guide (Which Model to Choose?)
- **Key-Value:** Need blazing-fast `GET/PUT` by single key; too simple for complex queries.
- **Column-Family:** Need massive write scale, time-series logs, or column analytics; less flexible for varied nested entities.
- **Graph:** Need deep multi-hop relationship traversal (referrals, fraud rings, routes); not for simple flat filtering.
- **Document (e.g., MongoDB):** Need flexible, evolving schemas, nested objects/arrays, secondary indexes, and rich developer-friendly queries.

## 12. Case Study Deep Dive: MongoDB (Document-Oriented NoSQL)

### 12.1 MongoDB Overview & Goal
- **Origin:** Name comes from **"Humongous"** (huge data); written in **C++**; created in **2009** by **10gen** (later MongoDB Inc.).
- **Design Goal:** Bridge the gap between **Key-Value stores** (fast & scalable, e.g., Memcached) and **Relational DBs** (rich query functionality & secondary indexes).
- **Definition:** Open-source, document-oriented database storing **JSON-like documents** with **dynamic schemas** (schema-free).

### 12.2 Relational Database vs. MongoDB Terminology

| Relational Database (RDBMS) | MongoDB |
| :--- | :--- |
| Database | Database |
| Table | **Collection** |
| Row / Record (Tuple) | **Document** |
| Column | **Field** |
| Primary Key | **`_id`** |
| `JOIN` | **Embedded documents / `$lookup`** |
| Index | Index |

### 12.3 Documents, BSON, Collections, Naming & `_id`

1. **Document:** Basic unit of storage consisting of `field: value` pairs.
   - Internally stored in **BSON (Binary JSON)** format (supports richer data types like `Date`, `ObjectId`, binary data, and faster traversal).
   - **Constraints/Limits:**
     - Field names **cannot start with `$`**.
     - Field names **cannot contain `.` (dot)** (in standard MongoDB naming rules).
     - **Maximum size of a single document = 16 MB**.

2. **Collection:** A group of MongoDB documents (analogous to a table).
   - **Unlike RDBMS:** There are **no rigid schema or integrity constraints** enforced by default across documents in the same collection:
     ```javascript
     use CollegeDB
     db.createCollection("students")
     db.students.insertMany([
       { name: "Rahul", age: 20 },
       { name: "Asha", department: "ECE" },
       { name: "Priya", age: 20, department: "CSE" }
     ])
     ```

3. **Naming Conventions:**
   - **Databases:** Meaningful names (`StudentDB`, `HospitalDB`, `LibraryDB`, `EcommerceDB`); avoid `db1`, `test123`, `abc`.
   - **Collections:** Meaningful lowercase plural names representing stored documents (`students`, `courses`, `employees`, `products`, `orders`).
   - **Fields:** Meaningful and consistent (`studentId`, `studentName`, `department` rather than `sid`, `n`, `d`).

4. **The `_id` Field:**
   - Every document in a collection **must have a unique `_id`** field acting as its primary key.
   - You can supply your own (`_id: 101`), or MongoDB automatically generates a globally unique 12-byte **`ObjectId("...")`**.

---

### 12.4 Capped Collections

A **capped collection** is a special fixed-size collection that behaves like a **circular buffer**: once it reaches its maximum capacity, MongoDB **automatically removes/overwrites the oldest documents** to make room for new inserts (preserving insertion order).

```javascript
// Capped by byte size (~100,000 bytes)
db.createCollection("logs", {
  capped: true,
  size: 100000
})

// Capped by BOTH byte size AND maximum document count (1,000 docs)
db.createCollection("recent_events", {
  capped: true,
  size: 100000,
  max: 1000
})
```

- **Suitable For:** Application/server logs, recent IoT sensor readings, temporary monitoring metrics, event streams, recent activity records.
- **Unsuitable For:** Permanent records (e.g., hospital patient medical histories, financial ledgers) because old data is silently evicted!

| Feature | Normal Collection | Capped Collection |
| :--- | :--- | :--- |
| **Maximum Size** | Grows dynamically | **Fixed** |
| **Old Data Automatically Removed?** | No | **Yes (FIFO circular eviction)** |
| **Good for Permanent Records?** | **Yes** | No |
| **Good for Logs / Temporary Streams?** | Possible | **Very Suitable** |
| **Manual Cleanup Required?** | Usually yes | **Often no** |

### 12.5 CRUD Operations, Query Operators & Case Study

**CRUD** stands for **Create, Read, Update, Delete**.

#### Comparison & Logical Operators

| Comparison Operator | Meaning | Logical Operator | Meaning |
| :--- | :--- | :--- | :--- |
| `$eq` | Equal to | `$and` | Joins clauses with logical AND (also implicit via comma) |
| `$ne` | Not equal to | `$or` | Joins clauses with logical OR |
| `$gt` / `$gte` | Greater than / Greater or equal | `$not` | Inverts the effect of a query expression |
| `$lt` / `$lte` | Less than / Less or equal | `$nor` | Joins clauses with logical NOR (matches none) |
| `$in` / `$nin` | Value is in / not in an array | | |

**Logical Query Examples:**
```javascript
// Implicit AND: CSE students with CGPA > 8
db.students.find({ department: "CSE", cgpa: { $gt: 8 } })

// Explicit $and
db.students.find({
  $and: [ { department: "CSE" }, { cgpa: { $gt: 8 } } ]
})

// $or: CSE students OR CGPA > 9
db.students.find({
  $or: [ { department: "CSE" }, { cgpa: { $gt: 9 } } ]
})
```

#### Worked Case Study: Police Station Database
Schema: `criminals` (`_id, name, crime, arrestDate`) and `firs` (`_id, FIR_No, date, officer, section`).

```javascript
// Sample Documents
// Collection 1: criminals -> { "_id": 1, "name": "Ravi", "crime": "Theft", "arrestDate": "2025-09-20" }
// Collection 2: firs      -> { "_id": 101, "FIR_No": "FIR001", "date": "2025-09-21", "officer": "Officer X", "section": "IPC 420" }

// a) List all FIRs registered by Officer X (Read)
db.firs.find({ officer: "Officer X" })

// b) Count crimes under IPC 420 (Read / Aggregate)
db.firs.countDocuments({ section: "IPC 420" })

// c) Find criminals arrested for Theft (Read)

// f) Update Officer for FIR001 (Update)

// g) Delete a criminal record (Delete)
```

### 12.6 Indexing in MongoDB

Without an index, MongoDB performs a **collection scan** (scanning all documents—terrible on 10 lakh / 8 million records). An **index** is a **B-tree / B-tree-like ordered data structure** mapping indexed field values to document locations (`1` = Ascending, `-1` = Descending).

#### Six Types of MongoDB Indexes

| Index Type | Syntax Example | Purpose / Notes |
| :--- | :--- | :--- |
| **1. Single-Field** | `db.students.createIndex({ regno: 1 })` | Speeds up queries filtering/sorting on one field (`-1` for descending). |
| **2. Compound** | `db.students.createIndex({ department: 1, semester: 1 })` | Index on multiple fields. **Field order matters!** Supports queries on `department` alone or `department + semester` (leftmost prefix), **not** `semester` alone efficiently. |
| **3. Multikey** | `db.students.createIndex({ skills: 1 })` | Automatically created when indexing a field holding an **array** (e.g., `skills: ["Python", "MongoDB", "Java"]`). |
| **4. Text** | `db.articles.createIndex({ title: "text", description: "text" })` | Full-text keyword search in articles/blogs/reviews using `$text: { $search: "artificial intelligence" }`. |
| **5. Geospatial** | `db.places.createIndex({ location: "2dsphere" })` | Location-based proximity queries (nearby restaurants, hospitals, taxi/delivery tracking). |
| **6. Unique** | `db.students.createIndex({ email: 1 }, { unique: true })` | Enforces uniqueness so no two documents share the same indexed value. |

### 12.7 Replication in MongoDB (Replica Sets)

MongoDB implements replication using a **Replica Set**—a group of `mongod` servers maintaining copies of the same dataset for **Availability, Fault Tolerance, and Load Balancing**.

```text
                Client Application / Driver
                     |               |
                   Writes          Reads (default)
                     v               v
                  +---------------------+
                  |       PRIMARY       |  <--- Maintains OPLOG
                  +----------+----------+
                     /              \
         Oplog Sync /                \ Oplog Sync
                   v                  v
          +-------------+        +-------------+
          |  SECONDARY  |        |  SECONDARY  |
          +-------------+        +-------------+
```

- **Oplog (Operation Log):** Every write goes to the **Primary**, which records the operation in its `oplog`. Secondaries periodically pull and apply `oplog` entries asynchronously to stay synchronized.
- **Automatic Failover & Election:**
  - Triggered when the Primary fails via **majority voting** (total voting members should be **odd**, e.g., 3 or 5, to prevent split-vote ties).
  - **During an election, no writes are accepted.** Once a Secondary wins majority votes, it becomes the new Primary.
  - When the crashed old Primary recovers, it rejoins the set as a **Secondary** after synchronizing.

#### Configuring Secondary Sites (Fine-Tuning)
- **`Priority = 0`:** Node **cannot be elected Primary** and cannot accept writes, but still holds data and **can serve client reads**.
- **`Hidden = True`:** Implies `Priority = 0`, **AND hidden from clients (cannot accept client reads/writes)**. Ideal for dedicated offline analytics, reporting, or backups without impacting production traffic.
- **`SlaveDelay = m`** *(modern MongoDB: `secondaryDelaySecs`)*: Should also set `Hidden = True`. Secondary lags `m` seconds behind the Primary before applying `oplog` entries—useful as a rolling safety buffer to recover from accidental bad transactions or `dropCollection` errors.

#### Default Read/Write Behavior & Read Modes
- **Default Write (`writeConcern: { w: 1 }`):** Writes go to Primary and succeed as soon as Primary accepts the write in memory (before Secondaries replicate it).
- **Default Read (`Primary`):** All reads go to Primary $\implies$ guarantees **Strict Consistency**.
- **5 Read Modes (Read Preferences):**
  1. `Primary` *(Default — always read from Primary)*
  2. `PrimaryPreferred` *(Primary if available; else Secondary)*
  3. `Secondary` *(Read only from Secondaries — may see stale data / eventual consistency)*
  4. `SecondaryPreferred` *(Secondary if available; else Primary)*
  5. `Nearest` *(Lowest network latency node, Primary or Secondary)*

### 12.8 Sharding in MongoDB & Practical Lab Mapping

- MongoDB shards collections horizontally across multiple servers (or Replica Sets) using a **Shard Key** and **`mongos` query router**, splitting e.g. a 1 TB collection into four 256 GB shards (`Shard A–D`).
- **Orthogonal to Replication:** Sharding divides data; Replication copies each shard for fault tolerance.
- **Practical Lab Alignment (`BACSE202` Indicative Experiments 10 & 11):**
  - **Exp 10 (CRUD & Scale-In / Scale-Out):** Creating databases/collections, CRUD operations (`insertOne`, `find`, `updateOne`, `deleteOne`), and adding (`sh.addShard(...)`) or draining/removing (`removeShard`) shards dynamically to scale out / scale in.
  - **Exp 11 (Replication, Backup, Restore & Data Sharing):** Configuring a Replica Set (`rs.initiate()`, `rs.add()`, `rs.status()`), performing logical backups and restores (`mongodump` / `mongorestore`), and inspecting how chunks/data are distributed across shards (`sh.status()`).

# Part III: Exam Prep, Worked Problems & Revision Quiz

## A. Worked Scenario: Indexing 8 Million Student Records

**Problem Statement:** A university stores **8 million student records** in MongoDB with frequent queries:
- **Q1:** Find a student using registration number (`regno`).
- **Q2:** Find all CSE students in Semester 5.
- **Q3:** Find all Semester 5 students irrespective of department.
- **Q4:** Find students having `"MongoDB"` in their `skills` array.

The DBA creates: `db.students.createIndex({ department: 1, semester: 1 })`.  
After indexing, **Q2** becomes much faster, but the other queries do not receive the same benefit.

1. **(a) Explain why the index is suitable for Q2 but not equally useful for Q3.**
   - **Answer:** `{ department: 1, semester: 1 }` is a **compound index** ordered first by `department` and then by `semester` (leftmost prefix rule). **Q2** filters on both `department` and `semester`, matching the index prefix directly. **Q3** filters only on `semester` without `department`; because `semester` values are scattered across every `department` entry in the B-tree, MongoDB cannot do a tight prefix lookup and falls back to a full collection scan (or much slower full index scan).

2. **(b) Recommend appropriate indexes for Q1 and Q4 and identify their types.**
   - **Answer:**
     - **Q1:** `db.students.createIndex({ regno: 1 }, { unique: true })` $\rightarrow$ **Unique Single-Field Index** (guarantees fast $O(\log N)$ lookup and enforces unique registration numbers).
     - **Q4:** `db.students.createIndex({ skills: 1 })` $\rightarrow$ **Multikey Index** (created automatically on array fields so each skill element is indexed individually).

3. **(c) A student suggests creating indexes on every field. Critically evaluate this suggestion.**
   - **Answer:** Indexing every field is a bad practice because:
     1. **Severe write overhead:** Every `insert`, `update`, or `delete` must update *all* B-tree indexes, slowing writes down drastically.
     2. **High RAM & disk consumption:** Indexes consume substantial memory (working set) and disk space across 8M documents.
     3. **Diminishing returns:** Unused indexes waste resources and add query planner overhead. Indexes should be chosen selectively based on frequent query patterns.

## C. Rapid Exam Revision Cheat Sheet

- **DDBMS Design Order:** Fragmentation $\rightarrow$ Allocation $\rightarrow$ Replication.
- **Fragmentation Reconstruction:** Horizontal uses **Union ($\cup$)**; Vertical uses **Natural Join ($\bowtie$)** (must retain PK).
- **Distributed Concurrency & Recovery:**
  - *Deadlock Prevention:* **Wait-Die** (non-preemptive), **Wound-Wait** (preemptive).
  - *Quorum Rule:* $N_r + N_w > N$ and $N_w > N/2$.
  - *Commit Protocols:* **2PC** (Prepare + Commit; **blocks** on Coordinator crash); **3PC** (adds `PreCommit`; non-blocking under fail-stop).
  - *Query Optimization:* **Semijoin ($\ltimes$)** ships only join keys first to slash network communication cost.
- **CAP Theorem:** Distributed systems always face Partitions (**P**), so choose **CP** (ATM, Flight Booking, Hospital) or **AP** (Instagram Likes, Google Maps Traffic). Single-node DBs look like **CA**.
- **ACID vs. BASE:** ACID (*Atomicity, Consistency, Isolation, Durability*) vs. BASE (*Basically Available, Soft State, Eventual Consistency*).
- **MongoDB Must-Knows:** BSON storage, `16 MB` max doc size, `_id` unique key, Compound index leftmost prefix rule, `oplog` replication, `Priority=0` / `Hidden=True` / `SlaveDelay`, Read modes, Hot Shards, Capped Collections.
